## 1. Current architecture (what exists in v0.3.0; read before changing)

- `scripts/catalog.py` single source of truth (54 entries). `scripts/package.py` builds `dist/material-grub/{scenes/<set>/{icons,bg}, res/<WxH>/(theme.txt, MG-*.pf2, bar/hl slices, logo_size, aspect), classes.json, rules.json, titles.json, palettes.json, scheme.txt, glyphs/, fonts/, bin/}`. Scene sets: `16x9`,`16x10`,`21x9`,`32x9` at 1080 high and `<set>@2` (2160 high) for screens >=1800 high. `--res`, `--scheme`, `--no-hints` options; release assets built by `.github/workflows/release.yml`; installer `--prebuilt` downloads them.
- Build time (`scripts/build_theme.py`, `scripts/render_scene.py`): `bg/<key>.png` (decor shapes, **cookie at top-right baked in**, hints baked in unless `--no-hints`) and `icons/<class>.png` (full hero scene for plain entries, hints baked in).
- Config time (root): `05_material` (grub.d; or `material-grub-static` for immutable) picks the bundle via `material-grub-assemble` (which applies `/etc/material-grub.conf` to `theme.txt` using `# mg:begin/end` blocks and `mgrub.load_conf`), `material-grub-classes` (annotates grub.cfg, unique `mg_*` per-entry classes, BLS mirrors, writes `/var/lib/material-grub/entries.json`), `material-grub-scenes` (Pillow: draws hero, info pills, gear/wrench, **section rail** on top of `bg` per entry; also draws the rail on class scenes).
- GRUB facts (hard-won, still true): no animation, no runtime recolour; `boot_menu` only draws whole items, so the theme is one full-screen **baked scene per entry** used as the boot_menu item icon; `image` ignores width/height (pre-scale files); boot_menu icons ARE scaled to `icon_width/height`; GRUB draws the FIRST-declared component on top; theme colours are global (countdown/raw-name colours are neutral); `blscfg` ignores `--path` here, mirrors must live outside `/boot/loader` on ostree; PF2 fonts must not contain "Google"/"GSF" in names (trademark terms, see `fonts/README.md`); keep OFL notices and "not affiliated with Google".
- `install.sh` is POSIX sh (dash/busybox tested), installs only missing deps, builds in /var/tmp, then `install/install.sh`. Immutable (ostree) layout exists (`material-grub-static`, `/var/lib/material-grub`).
- Tests: `sh tests/run.sh` (syntax, unit, fake-/boot pipeline test), `tests/boot_smoke.py` (QEMU+OVMF), CI in `.github/workflows/ci.yml` (boot job runs in a Fedora container because Debian GRUB lacks blscfg.mod).

## 2. Target design

### 2.1 Options model (all runtime-selectable; no asset multiplication)
`/etc/material-grub.conf` (+ installer flags + TUI) gets:

| Key | Values | Default | Notes |
|---|---|---|---|
| `STYLE` | `rail` \| `clean` \| `list` | `rail` | `rail` = today. `clean` = full screen, **no rail**, with the first-version peek panels and top/bottom label chips (section 2.4). `list` = new. |
| `SCHEME` | `dark` \| `light` | `dark` | stays a build/asset choice (palettes are baked in `palettes.json`); recorded in conf for TUI/summary only |
| `LOGO` | `on` \| `off` | `on` | BGRT firmware image inside the cookie |
| `COOKIE` | `on` \| `off` | `on` | the whole top-right cookie shape; `COOKIE=off` implies no logo |
| `HINTS` | `on` \| `off` | `on` | key-hint pills (`--no-hints` becomes sugar for `HINTS=off`) |
| `RAW_NAME`, `COUNTDOWN`, `TIMEOUT` | as v0.3 | | unchanged |

**Key architectural move (Phase 0): make style a RUNTIME choice.** Today hints and the cookie are baked into `bg`/`icons` PNGs at build time, so each style/option would multiply the 24 release assets. Instead: build time produces `bg/<key>.png` WITHOUT cookie and WITHOUT hints, and `icons/<class>.png` hero scenes WITHOUT hints/cookie; `material-grub-scenes` draws cookie, hints, rail/list at config time (it already composes the rail). Result: one asset set serves every style; `material-grub-apply` switches style in seconds. Keep `--no-hints` working (writes `HINTS=off`).

### 2.2 Shared renderer module
Refactor `install/bin/material-grub-scenes` into an importable module (`install/bin/mgscenes.py`: pure functions `render_entry(entry, menu, style, palette, opts) -> Image`, `render_cookie`, `render_hints`, `draw_rail`, `draw_list`) plus a thin CLI. It must stay stdlib+Pillow, importable without side effects, and usable from `scripts/` (distro gallery) and later a Ventoy target (see 2.6). Everything scales with `S = scene_height/1080` (existing `u()` helper).

### 2.3 Menu model (needed by `list`, and fixes a latent gap)
The list must know the **siblings of the selected entry in real GRUB menu order, per menu level**. `material-grub-classes` currently writes an unordered `entries.json`. Extend it to also write `menu.json`: `[{"level":"top","items":["mg_..",...]},{"level":"adv","items":[...]}]` in the order they appear in the generated menu (walk grub.cfg in file order; expand the BLS structure at the `blscfg` position: default kernel, Advanced submenu, then remaining entries; the immutable raw-fallback submenu is NOT listed). Plain entries (Windows, Firmware, Restart, Shut down) need **unique per-entry classes in `list` style** (two Windows installs, duplicates) — currently plain entries use the shared class scene `icons/<key>.png`; in `list`/`clean` style also bake per-entry scenes for them.

### 2.4 `clean` style (clarified by the maintainer)
"Top and bottom hints" = **the little top and bottom label chips with a peek of the neighbouring options, as in the very first version** (see `mockup()` in `scripts/render_scene.py`, and `git log` for the early design). A different look from `rail`, not a rail-less copy of it:
- Layout from that mockup (1080-high design values, scale with `u()`): the current entry's rounded panel fills the middle (`ph=888`, `top=96`, 12 px gap, 24 px side margins, rounded 64 px corners); the **previous entry's panel peeks in above it and the next entry's panel below it** (about 84 px of each visible), each in ITS OWN palette colour, so the neighbours' colours are visible at the screen edges while the whole centre follows the selected entry.
- Each panel carries a small **label chip** (entry icon + name, `chip()` in `render_scene.py`) at its top and bottom edge, centered; in the peek bands you therefore see the previous entry's bottom chip at the top of the screen and the next entry's top chip at the bottom. Wrapping: first/last entry peek at the last/first (as `mockup()` does with modulo) or show nothing; prototype and show both.
- Needs the sibling order, i.e. `menu.json` (section 2.3). Which neighbours: the previous/next entry in the same menu level (so inside Advanced they are the other kernels); `advanced`/`rescue` chips keep the gear/wrench second icon like in list rows.
- The hero content (cookie, hero pill, name, pills, countdown) as today, no rail. Key-hint pills remain controlled by `HINTS` (the first version had them inside the panel above the bottom chip); decide placement when prototyping so they do not collide with the chips.
- Colours: peek panels use the neighbour's `surface`/`surfaceContainer` (their own palette), chips use the neighbour's `surfaceContainerHigh`/`onSurface`/`primary`.
- No GATE needed for the content any more; still show a prototype screenshot (dark + light, Fedora with Advanced, Windows) to the maintainer before polishing, since it is a new design pass of an old look.

### 2.5 `list` style (the main new feature)
Same palette, Google Sans Flex, glyphs, section dividers; the **whole list is baked into the scene** (one scene per entry = list with that entry highlighted), centered, whole background in the selected entry's palette:
- Column centered horizontally and vertically, about 640 px wide at 1080 high (all in `u()`).
- Row = **icon inside an M3 shape** (cookie by default; try `sunny`/`flower`/`clover`/pill, shapes already in `render_scene.py`; move shape masks into the shared module) + **name inside a pill**. Selected row: selection box (pill/rounded rect in `primaryContainer`, name in `onPrimaryContainer`), unselected rows use the selected palette's `surfaceContainerHigh`/`onSurface` (same logic as the rail). Optionally tint each row's shape with its own palette accent (prototype both).
- `advanced` and `rescue` rows keep their second icon (gear / wrench): placed **right before the name**, name shifted right to make room. Kernel rows inside Advanced: label = kernel version (fall back to title); rescue = "Rescue"; advanced = "Advanced options".
- **Section dividers** (Linux | Windows | System) kept exactly like the rail's divider line/spacing, between groups (groups come from `groups_of`).
- Overflow: when rows exceed the available height, show a window of N rows kept around the selection with "+K more" chips (never clip a row). Must work with 1 entry and 20+ entries (many kernels).
- Countdown bar/label and raw-name line stay where theme.txt puts them (check they don't collide with the list; move per style in `theme.txt` via the generated theme, not hacks). BGRT cookie/logo as per `COOKIE`/`LOGO`.
- Hints (`HINTS=on`) bottom, same as other styles.
- Everything must work for all 4 aspect sets and the 2160-high sets (use `S`).

### 2.6 Ventoy (NOT in this task; only keep the door open)
Do not build Ventoy support. Just keep the renderer pure and parameterised (palette, entries, menu, style in; Image out) so a later Ventoy target can pre-render a fixed catalog. Note in docs only.

### 2.7 TUI installer
- `install.sh` stays the entry point (POSIX sh, still works non-interactively with all existing flags). New flags: `--tui` (force), `--no-tui`, `--style`, `--cookie/--no-cookie`, `--logo/--no-logo` (as applicable), `--hints/--no-hints`. The TUI starts only when stdin/stdout are a TTY, `--yes`/`--no-tui` are absent and at least one required choice (resolution, style, scheme) was not given by flag. Otherwise auto-detect/default as today.
- Implementation: `install/tui.py` (stdlib `curses`), started by `install.sh` after python3 is available (it already is a requirement; on a host without python3 the TUI is skipped and the current behaviour applies). If `curses` is unavailable or `TERM` is dumb: plain line prompts with the same questions. The TUI only COLLECTS answers and prints/returns them as shell-safe `KEY=value` lines; `install.sh` keeps doing the work (no logic duplication; the final summary also prints the equivalent non-interactive command line).
- Layout (maintainer's spec): **left pane** = (top) the current question with its options, selected by arrows/Enter; (below) a tab-like **summary strip** showing answered steps and what is still to answer, becoming the final confirmation screen. **Right pane** = a small call-out box explaining the currently highlighted option (for `STYLE` also a tiny ASCII wireframe). Footer key hints. Resizes cleanly; works at 80x24.
- Question order: 1 Resolution -> 2 Style (rail / clean / list) -> 3 Colour scheme (dark / light) -> 4 Firmware logo & cookie (cookie + logo / cookie only / none) -> 5 Hints (on/off) -> 6 Extras (raw name line, countdown, timeout) -> 7 Install source (prebuilt download vs build from source; only when prebuilt is possible; immutable hosts: explain the layout and ask consent, replacing the old y/N prompt) -> 8 Summary & confirm.
- **Resolution**: detect the **primary monitor**, show it, ask "is this correct?"; if not, offer the other detected monitors and a free-text `WxH` field (validated against `^[0-9]{3,5}x[0-9]{3,5}$`, snapped like today). Detection order (best effort, never fatal): X11 `xrandr --query` primary (run as `$SUDO_USER` with its DISPLAY/XAUTHORITY when available) -> Wayland via `gdbus` org.gnome.Mutter.DisplayConfig / `kscreen-doctor -j` / `wlr-randr` as the sudo user -> DRM sysfs: connected internal panel (`eDP`/`LVDS`/`DSI`) first, else the connected output with the largest preferred mode -> `GRUB_GFXMODE` from `/etc/default/grub` (offer it as "current GRUB setting") -> 1920x1080. Callout must say GRUB draws on whichever output the firmware picks (usually the primary), and that the monitor's native mode is best.
- Testable: drive it with a pty in `tests/` (python `pty` + scripted keys) at 80x24; unit-test the resolution parsers with fixture outputs.

### 2.8 Distro gallery (README + docs)
- New `scripts/gen_distro_table.py`: for every catalog entry render a sample scene with the shared renderer (dark, 16x9, 1x, e.g. kernel-style scene with the pills for a Linux distro; plain scene for Windows/Firmware/Restart/Shut down) and write downscaled thumbnails (about 480x270, quantized PNG or WebP) to `docs/distros/<key>.png`, plus the generated table between `<!-- distros:begin -->` / `<!-- distros:end -->` in `docs/distros.md` and a compact grid (or `<details>` block with the full table) in the README. Columns: logo/sample | name | key | seed colour (source: chosen/si/proposed) | matched names (aliases) | "not listed?" link to the distro request template.
- CI: a job runs `python scripts/gen_distro_table.py --check` and fails if the generated Markdown differs from the committed one or an image is missing (do NOT byte-compare PNGs: Pillow/FreeType versions differ; compare the table text + file list). A manually triggered/`workflow_dispatch` job regenerates and uploads images as an artifact.
- Also show the new styles in the README gallery (rail, clean, list; dark + light).

## 4. Definition of done
- `sh tests/run.sh` and all CI jobs green; QEMU-verified screenshots for each style and scheme in at least 1920x1080, 2560x1080 and 3840x2160; list style verified with BLS Advanced submenu and with the classic Debian-style layout; overflow case verified.
- `rail` unchanged for existing users (same default; existing conf files keep working; `--no-hints`, `--scheme`, `--prebuilt` unchanged).
- README: options table, style gallery, distro table; CHANGELOG "Unreleased"; installer `--help` text consistent.
- Honest PR description: list what was and was NOT verified (real hardware, immutable, 5120-wide modes cannot boot in QEMU/OVMF).

## 5. Risks / traps to remember
- Baked per-entry list scenes multiply config-time work: render with `ProcessPool` if slow; entry counts are small, but measure at 3840x2160.
- `entries.json` order is not menu order today; `menu.json` is required before `list` can be right.
- Plain entries share class scenes; list needs unique scenes.
- Moving cookie/hints to runtime changes `material-grub-scenes` inputs: keep `dist/` bin copies in mind (package copies `install/bin` at package time; tests use `install/bin` directly, QEMU tests use `dist/`; always re-run `package.py` before QEMU tests).
- `make screenshots` OVERWRITES `docs/screenshots/*`: never run it casually; revert with `git checkout docs/screenshots`.
- 5120-wide modes cannot be booted in QEMU/OVMF; say so, never claim verified.
- Release workflow builds assets only on `v*` tags; the tag must equal `VERSION`.
- Keep the Google trademark rules for fonts; keep OFL files verbatim.
