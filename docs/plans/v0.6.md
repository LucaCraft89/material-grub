# 0.6.0 plan: safety, maintainability, packaging

Status: IN PROGRESS. Done: A1, A2, A3, B4, B5. Everything else is still planned. Branch `release/0.6.0`, one PR, one commit per item.
Source: a full review of 0.5.0 on 2026-11-18; decisions by the maintainer in the same conversation.

## Decisions (maintainer)
- No prebuilt downloads, ever. Everything is built from source (packages included).
- The installer's logic moves to Python and must work on every supported distro. Minimum Python: **3.8**.
- Requirements are pinned to exact versions with hashes.
- Packaging: AUR PKGBUILD, Fedora RPM spec (COPR), Debian .deb. The AUR is not accepting registrations right now, so the PKGBUILD is written and tested but cannot be published yet (publish later).
- Updates must come through the normal package manager (`dnf upgrade`, `apt upgrade`, `pacman -Syu`, ...) and every update goes through the same safety nets and fallbacks as `install.sh` (validate, roll back, notify).
- Per-entry customisation (overrides file) is **on hold**, not in 0.6.0.
- The PNLug logo is used with the owner's permission. It stays in the repo; THIRD_PARTY.md is reworded, no change to the packaging.
- Whenever a step needs `sudo` on the maintainer's PC (fingerprint), the assistant says so first, so the finger is ready.

## Order of work
Items are ordered so that tests and tooling come first and later items are built on top of them.

### A. Tooling and hygiene (no behaviour change)
1. **[DONE] Lint and format in CI.** `ruff` (lint + format) and `shellcheck` jobs. Rename `install/bin/material-grub-*` Python tools to importable modules (`.py`), keeping thin executables with the old names so installed paths do not change. Split the 200 to 300 character lines. This is a large mechanical diff, so it is its own commit with no logic changes, verified by the whole existing test suite. Done as: `pyproject.toml` (ruff: E, F, W, I, B, UP; E501 ignored because the formatter wraps code and long comments/messages stay as written), a `lint` CI job, tools in `install/bin/cmd_*.py` with a `main()` and thin `material-grub-*` wrappers, shellcheck at warning level. Built theme assets are byte-identical before and after; `rules.json` differs only in the order of equal-length rules, which was already non-deterministic at HEAD (set iteration in `scripts/package.py`; to be fixed in item 2).
2. **[DONE] Single source of truth for shared lists.** One `resolutions.json` (read by `package.py`, the installer, the TUI, `material-grub-assemble`, the README table generator) and one shared `GENERIC` set. A test fails if any list drifts. Fix `key_of` in `material-grub-ventoy` (the docstring after the first `return`). Done as: `install/bin/resolutions.json` plus `mgrub.RESOLUTIONS`, `mgrub.GENERIC`, `mgrub.snap()` and a small `mgrub.py list|snap` CLI for `install.sh`; README table is checked by a test instead of generated; `rules.json` ties are now sorted deterministically.
3. **[DONE] Pinned requirements.** `requirements.txt` with `==` versions and hashes, installed with `--require-hashes`; a `make update-requirements` helper; CI check that the pins install cleanly. Done as: `requirements.in` (newest release per Python range) -> `requirements.txt` via `scripts/update_requirements.py` (hashes of every release file from PyPI), CI job on Python 3.9, 3.10, 3.11, 3.13 in containers, installed with `--require-hashes` everywhere. **Finding:** `materialyoucolor` ships no wheel for Python 3.8 (its sdist needs a C compiler), so the build needs Python 3.9+. The installer itself stays 3.8-compatible; item 8 must find a 3.9+ Python for the build step (RHEL 8 has `python39`).

### B. Safety net for the GRUB rewrite
4. **[DONE] Real GRUB-script parser instead of regex surgery** in `material-grub-classes` / `material-grub-static`. A small tokenizer for GRUB script (quotes, escapes, `{}` nesting, multi-line entry headers, comments) that finds `menuentry` and `submenu` blocks and inserts classes. It replaces the line-by-line regex and the `}`-counting. New tests with hostile titles: quotes, escaped quotes, `}` and `{` inside titles, unicode, very long titles, multi-line headers, nested submenus. The old behaviour stays the reference for normal files (golden-file tests from real Fedora, Debian, Ubuntu, Arch `grub.cfg` samples). Done as: `install/bin/grubscript.py` (tokenizer + block finder), used by `cmd_classes.py` and the insertion point in `cmd_static.py`; `tests/test_grubscript.py` with `tests/golden/` (real `grub-mkconfig` output made in the four distro containers; the annotated references are the 0.5.0 regex tool's output, reproduced byte for byte by the parser).
5. **[DONE] Validate and roll back.** After every write of `grub.cfg` run `grub-script-check` (`grub2-script-check` on Fedora). If it fails, or the theme assembly is incomplete, restore the previous `grub.cfg` automatically, leave the system on its old working menu, and print a clear message. Also generated into `grub.cfg`: if the theme file or the icons directory is missing at boot, skip `set theme` so the menu falls back to plain GRUB.
   **User notification:** the rollback prints a box in the terminal (installer or `material-grub-apply`) and writes to the journal (`logger -t material-grub`). When it runs from the path unit (no terminal), it also sends a `wall` message and drops a note in `/var/lib/material-grub/last-error`; `doctor` (item 9) shows that note. Done as: `install/bin/mgsafe.py` (structure check with the scanner, `grub-script-check`, theme completeness, box/logger/wall/last-error) and `cmd_postprocess.py` (`material-grub-postprocess`, called by `postprocess.sh`) which wraps classes, static and scenes in `mgsafe.guarded`; `material-grub-assemble` keeps the old theme when the new one is incomplete and swaps directories with the old one kept until the new is in place; the generated `grub.cfg` skips `set theme` when `theme.txt` or `icons/` is missing at boot. A grub.cfg that failed is not retried on identical input (no path-unit loop) unless `MG_FORCE=1` (the installer and `material-grub-apply` set it). Tests: `tests/test_safety.py`. Behaviour note: a crash of the scene renderer now also rolls back (it used to be ignored).
6. **`--dry-run`.** Builds everything in a scratch directory and prints a unified diff of `grub.cfg` and `/etc/default/grub` plus the list of files it would write; changes nothing. (`--stage-only` already exists and keeps meaning "build only, do not touch GRUB"; `--dry-run` shows what the touch would be.)
7. **Tests for items 4 to 6:** unit tests, the fake-`/boot` pipeline test, CI installer matrix, the QEMU boot job, plus a run on the maintainer's own PC (see "Testing").

### C. Installer in Python (works on every distro)
8. **`install.sh` becomes a thin POSIX-sh bootstrap**, `install/installer.py` does the work. The shell part only: checks it is root when needed, finds or installs a Python 3.8+ with the distro's package manager (dnf, apt, pacman, zypper, apk, xbps), then `exec`s the Python installer. On RHEL 8 / Alma 8 / Rocky 8 where `python3` is 3.6, it installs `python38`/`python39` and uses that. Python code: argument parsing, TUI glue, dependency detection, resolution snapping (the inline snippet goes away), build, Ventoy path, immutable path. Same flags, same output steps, same exit behaviour (`--help` text unchanged). Tested by driving the installer in the six CI containers plus an extra RHEL-family container with the old Python.

### D. User-facing features
9. **`material-grub-apply --status` / `material-grub doctor`.** Checks: theme directory present and complete for the configured resolution, `grub.cfg` annotated and passes `grub-script-check`, every menu entry has a scene, hooks installed and executable, path unit enabled and active, `/etc/material-grub.conf` valid (unknown keys and bad values reported), last-error note from item 5, installed version vs `VERSION`. Exit code 0/1 so it can be scripted. Output is meant to be pasted into a bug report; the bug template asks for it.
10. **Preview without QEMU and without root.** `./install.sh --preview` (and `material-grub preview`): reads the user's real boot entries (from `grub.cfg` / `/boot/loader/entries` read-only, or a sample list when unreadable), renders every scene for the chosen style, scheme and resolution into a temporary directory with the existing Pillow renderer, and opens a single self-contained HTML contact sheet (and writes PNGs) in the browser. Nothing is installed, nothing under `/boot` or `/etc` is touched, no VM. Limits that the preview page states: it is a render of the scenes, not GRUB itself (the real GRUB menu behaviour is tested by the QEMU jobs).

### E. Packaging (built from source, no prebuilt assets)
11. **`packaging/` directory:** `arch/PKGBUILD`, `rpm/material-grub.spec`, `debian/` (control, rules, postinst/prerm, `/etc/kernel/postinst.d` and `/etc/kernel/postrm.d` hooks). The package builds the theme in the build step (`package.py`) with the pinned requirements and installs the same files `install/install.sh` does; the package triggers (pacman hook, RPM `%posttrans`, dpkg trigger) re-run `material-grub-apply`. Build-tested in Arch, Fedora and Debian containers in CI (`makepkg`, `rpmbuild`, `dpkg-buildpkg`) and an install-then-apply smoke test. Publishing (AUR, COPR, a PPA or plain release files) is done by the maintainer; a `docs/packaging.md` explains how to cut each one from a tag. Note: the maintenance cost is three files to bump per release; a `scripts/bump_version.py` updates `VERSION`, the spec, PKGBUILD and the Debian changelog together.

### E2. Automatic updates through the package manager
A plain `apt upgrade` / `dnf upgrade` / `pacman -Syu` must fetch the newest release and apply it safely, with no manual step.
- **Repositories (built from source, no prebuilt theme downloads):** Fedora/RHEL: COPR (COPR builds the SRPM itself). Arch: AUR when registrations reopen (until then users can use the PKGBUILD from the repo). Debian/Ubuntu: the open point below.
- **Every upgrade runs the same pipeline as the installer:** the package's post-install/post-transaction step calls `material-grub-apply --from-package`, which does: back up the current `grub.cfg` and `/etc/default/grub` (same `/var/backups/material-grub` store), assemble, annotate with the parser, `grub-script-check`, `doctor`; on any failure it restores the previous `grub.cfg`, keeps the previously working theme directory (assembled into a new directory and swapped atomically, the old one kept until the new one has passed the checks), records `/var/lib/material-grub/last-error` and notifies (journal, `wall`, package manager output).
- **The package manager must never fail or leave the bootloader half-written because of us:** the hook exits 0 after a rollback (the update itself is not blocked, the failure is reported loudly), and a failed or interrupted upgrade leaves the old working setup in place. Downgrades and reinstalls are handled the same way.
- `/etc/material-grub.conf` is a config file: never overwritten (`%config(noreplace)`, dpkg conffile, pacman `backup=`).
- Kernel updates keep working through the same hook (kernel postinst/postrm, pacman hook, `%posttrans`), already covered by item 11.
- The config version is checked on upgrade (a `CONF_VERSION` key) so a future format change migrates instead of breaking.
- Tests: in the Arch, Fedora and Debian containers, install version N-1, upgrade to N, check `doctor`; plus a broken-upgrade case (corrupt scene set) that must roll back and leave a bootable `grub.cfg`.
- **OPEN, ask the maintainer before building:** for Debian/Ubuntu a plain `apt update` needs an apt repository. A signed repo on GitHub Pages would host built `.deb` files, which conflicts with "no prebuilds"; a Launchpad PPA builds from source but is Ubuntu only. The maintainer must choose, and also create the signing key / PPA / COPR project (account-bound steps the assistant cannot do).

## Testing
Every item must pass `sh tests/run.sh` and the full CI before it is committed to the PR.
- **CI:** existing jobs plus ruff, shellcheck, parser fixtures, the old-Python container, packaging builds.
- **QEMU/OVMF** (existing `boot_smoke.py`, `ventoy_smoke.py`) for items 4, 5 and 8, including a deliberately broken `grub.cfg` to prove the rollback and the plain-menu fallback.
- **On the maintainer's PC (Fedora 44, real GRUB):** after items 4 to 6 and 8, a real `sudo ./install.sh --dry-run`, then a real install, reboot check, `doctor`, uninstall. The assistant announces every `sudo` command before running it so the fingerprint can be ready, and checks first that `/var/backups/material-grub` holds the original files. The assistant will not run an install on the real bootloader without the maintainer saying go.

## Risks
- Item 1 (reformat) touches nearly every file; kept as a separate no-logic commit to make the rest reviewable.
- Item 4 is the riskiest logic change; the golden-file tests and the rollback in item 5 exist to contain it. Item 5 lands before item 4 is relied on in the installer path.
- Item 8 changes the entry point of the installer; the shell bootstrap is kept tiny and shellchecked so that a failure there is easy to reason about.
- Packaging (item 11) adds maintenance; the version-bump script is there to keep it small.

## Out of scope
Prebuilt downloads, per-entry overrides (on hold), NixOS support.
